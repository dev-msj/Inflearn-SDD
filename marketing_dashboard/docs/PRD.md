# PRD: Marketing Dashboard

> GitHub 활동 데이터를 AI로 분석해 개인 브랜딩 콘텐츠 초안을 자동 생성하는 개인용 대시보드

| 항목 | 내용 |
|---|---|
| 문서 버전 | v1.0 |
| 작성일 | 2026-08-11 |
| 상태 | MVP 정의 완료 |
| 제품 유형 | 개인용 웹 대시보드 (1인 사용자) |
| MVP 기능 수 | 3개 (F1, F2, F3) |

---

## 1. 개요 및 문제 정의

### 1.1 배경

개발자는 매일 커밋을 쌓고, PR을 머지하고, 이슈를 해결한다. 이 활동은 GitHub에 자동으로 기록되지만, **기록되는 것과 알려지는 것은 다르다.** 개인 브랜딩 관점에서 GitHub 프로필은 "잔디"라는 시각적 요약만 제공할 뿐, "이 사람이 무엇을 만들었고 어떤 문제를 풀었는가"를 외부에 설명해 주지 않는다.

그 설명을 하는 채널이 LinkedIn, X, 기술 블로그다. 하지만 대부분의 개발자는 이 채널을 비워둔다. 이유는 동기 부족이 아니라 **마찰(friction)** 이다:

1. **회상 비용**: "지난 2주에 내가 뭘 했더라?"를 떠올리려면 커밋 로그를 직접 뒤져야 한다.
2. **번역 비용**: 커밋 메시지(`fix: resolve race condition in worker pool`)는 개발자용 언어다. 이를 비개발자도 이해할 수 있는 성과 서사로 바꾸는 작업은 별개의 노동이다.
3. **재작성 비용**: 같은 소재라도 LinkedIn(길고 전문적), X(짧고 후킹), 블로그(구조화된 상세 설명)는 형식이 전혀 다르다. 한 번 쓴 글을 세 번 다시 써야 한다.

이 세 가지 마찰의 합이 "쓸 내용은 있는데 안 쓰게 되는" 상태를 만든다.

### 1.2 문제 정의

> **개발자에게는 공유할 만한 성과가 이미 GitHub에 축적되어 있으나, 그것을 회상하고 · 서사로 번역하고 · 플랫폼별로 재작성하는 비용 때문에 실제 콘텐츠 발행으로 이어지지 않는다.**

### 1.3 해결 방향

GitHub 활동 데이터를 자동 수집하고, AI가 이를 분석해 "무엇을 했는가"를 인사이트로 정리하며, 세 플랫폼 각각의 형식에 맞는 초안을 동시에 생성한다. 사용자는 백지에서 시작하는 대신 **수정 가능한 초안에서 시작한다.**

### 1.4 제품 한 줄 정의

**"GitHub 로그인 → 기간 선택 → 3개 플랫폼용 콘텐츠 초안 완성"을 5분 안에 끝내는 개인용 대시보드**

## 2. 타겟 사용자

### 2.1 주 사용자 (Primary — MVP의 유일한 대상)

**개인 개발자 본인 (1인 사용자)**

| 속성 | 내용 |
|---|---|
| 규모 | 1명 (제품 소유자 본인) |
| 기술 수준 | 개발자. GitHub OAuth, API 개념에 익숙함 |
| 목적 | 자신의 GitHub 활동을 소재로 개인 브랜딩 콘텐츠 제작 |
| 사용 빈도 | 주 1회 ~ 월 2회 (주간/격주 회고 시점) |
| 사용 맥락 | 데스크톱 브라우저. 짧은 세션(5~10분) 내 초안 확보 후 각 플랫폼에 직접 붙여넣기 |

### 2.2 사용자 시나리오

> 금요일 오후, 이번 주 작업을 마무리한 개발자가 대시보드에 접속한다. GitHub으로 로그인하고 기간을 "최근 7일"로 선택한다. 대시보드가 이번 주 커밋 34개, 머지된 PR 5개, 닫은 이슈 3개를 보여준다. "분석" 버튼을 누르니 AI가 "인증 모듈 리팩터링과 API 응답 속도 개선이 이번 주의 핵심 작업"이라고 요약한다. "콘텐츠 생성"을 누르면 LinkedIn용 장문 포스트, X용 짧은 트윗, 블로그용 개요가 동시에 나온다. 마음에 들지 않는 표현 몇 개를 직접 고치고, 복사 버튼으로 각각 복사해 실제 플랫폼에 붙여넣는다.

### 2.3 비대상 사용자 (MVP 범위 밖)

- 팀 / 조직 단위 사용자 — 다중 사용자 인증·권한 설계 불필요
- 마케터, PM 등 비개발 직군 — GitHub 활동이 소재가 아니므로 대상 아님
- 대행사 / 다계정 관리자 — 타인의 계정을 대신 운영하는 시나리오 미지원

### 2.4 설계에 미치는 영향

사용자가 1명이라는 사실은 다음을 **의도적으로 단순화**할 근거가 된다:

- 인증: GitHub OAuth 단일 제공자. 자체 회원가입/비밀번호/이메일 인증 없음
- 권한: 역할(Role) 개념 없음. 로그인한 사용자 = 자신의 데이터만 접근
- 저장소: 사용자별 데이터 격리 설계 불필요 (DB 자체가 없음)
- 확장성: 동시 접속자 수, 멀티테넌시 고려 불필요

## 3. 핵심 기능 (MVP)

MVP는 **정확히 3개 기능**으로 구성된다. F1 → F2 → F3는 데이터가 순차적으로 흐르는 파이프라인이며, 각 단계는 앞 단계의 산출물을 입력으로 받는다.

```
[F1] GitHub 로그인 + 활동 수집  →  [F2] AI 활동 분석/요약  →  [F3] 플랫폼별 콘텐츠 생성
     (원시 활동 데이터)              (인사이트·하이라이트)        (LinkedIn/X/블로그 초안)
```

---

### F1. GitHub OAuth 로그인 + 활동 데이터 수집

#### 개요

사용자가 GitHub 계정으로 로그인하면, 지정한 기간 동안의 활동 데이터(커밋, PR, 이슈, 스타 등)를 GitHub API로 조회해 대시보드에 표시한다.

#### 사용자 스토리

> **개인 개발자로서**, GitHub 계정으로 한 번 로그인하고 기간만 선택하면 그 기간의 내 활동이 자동으로 모여 보이기를 원한다. **왜냐하면** 커밋 로그와 PR 목록을 저장소마다 일일이 뒤지며 "내가 뭘 했는지" 회상하는 데 드는 시간이, 정작 글을 쓰는 시간보다 길기 때문이다.

#### 수용 기준

**AC-1.1 — 로그인 진입**
- **Given** 로그인하지 않은 사용자가 대시보드 루트 경로에 접속했을 때
- **When** 페이지가 렌더링되면
- **Then** "GitHub으로 로그인" 버튼이 표시되고, 활동 데이터 영역과 분석/생성 기능은 노출되지 않는다

**AC-1.2 — OAuth 인증 성공**
- **Given** 사용자가 "GitHub으로 로그인" 버튼을 클릭했을 때
- **When** GitHub OAuth 동의 화면에서 접근을 승인하면
- **Then** 대시보드로 리다이렉트되고, 헤더에 사용자의 GitHub 아바타와 로그인 ID가 표시된다

**AC-1.3 — OAuth 인증 거부/실패**
- **Given** 사용자가 GitHub 동의 화면에서 "취소"를 누르거나 OAuth 콜백이 에러를 반환했을 때
- **When** 대시보드로 돌아오면
- **Then** "GitHub 로그인에 실패했습니다. 다시 시도해 주세요."라는 오류 메시지와 재시도 버튼이 표시되며, 애플리케이션이 흰 화면이나 처리되지 않은 예외 상태로 빠지지 않는다

**AC-1.4 — 기간 선택**
- **Given** 로그인한 사용자가 대시보드에 있을 때
- **When** 기간 선택 컨트롤을 확인하면
- **Then** 최소 `최근 7일`, `최근 30일`, `최근 90일` 3개 옵션이 제공되고, 기본값은 `최근 7일`로 선택되어 있다

**AC-1.5 — 활동 데이터 수집 항목**
- **Given** 로그인한 사용자가 기간을 선택했을 때
- **When** 활동 데이터 조회가 완료되면
- **Then** 해당 기간의 아래 4개 항목이 각각 **건수와 함께** 화면에 표시된다
  - [ ] 커밋(Commit) 수
  - [ ] Pull Request 수 (생성/머지 상태 구분 포함)
  - [ ] 이슈(Issue) 수 (생성/종료 상태 구분 포함)
  - [ ] 스타(Star)를 준 저장소 수
- **And** 각 항목별로 어떤 저장소에서 발생했는지 **저장소명이 함께 표시**된다

**AC-1.6 — 로딩 상태**
- **Given** 활동 데이터 조회가 진행 중일 때
- **When** 응답이 아직 도착하지 않았으면
- **Then** 로딩 인디케이터가 표시되고, "분석" 및 "콘텐츠 생성" 액션은 비활성화된다

**AC-1.7 — 활동 없음 처리**
- **Given** 선택한 기간에 활동 데이터가 0건일 때
- **When** 조회가 완료되면
- **Then** "선택한 기간에 활동 기록이 없습니다. 다른 기간을 선택해 보세요."라는 안내가 표시되고, "분석" 버튼은 비활성 상태를 유지한다

**AC-1.8 — API 오류 처리**
- **Given** GitHub API 호출이 실패했을 때(rate limit 초과, 네트워크 오류, 토큰 만료 등)
- **When** 오류 응답을 받으면
- **Then** 실패 원인을 구분한 사용자 메시지가 표시된다
  - rate limit 초과 → "GitHub API 호출 한도를 초과했습니다. 잠시 후 다시 시도해 주세요."
  - 토큰 만료/무효 → 재로그인 유도 메시지 및 로그인 버튼
  - 그 외 → 일반 오류 메시지 및 재시도 버튼

**AC-1.9 — 로그아웃**
- **Given** 로그인한 사용자가 로그아웃을 실행했을 때
- **When** 처리가 완료되면
- **Then** 세션이 종료되어 로그인 전 화면으로 돌아가고, 화면에 표시되던 활동 데이터·분석 결과·생성 콘텐츠가 모두 화면에서 제거된다

### F2. Gemini API 기반 활동 분석 요약

#### 개요

F1에서 수집한 원시 활동 데이터를 Gemini API에 전달해, "이 기간에 무엇을 했는가"를 사람이 읽을 수 있는 인사이트와 하이라이트로 도출한다.

#### 사용자 스토리

> **개인 개발자로서**, 흩어진 커밋 메시지와 PR 제목이 아니라 "이번 기간의 핵심 작업은 무엇이었고 어떤 의미가 있었는가"라는 정리된 서사를 보고 싶다. **왜냐하면** 콘텐츠의 소재는 개별 커밋이 아니라 그 커밋들이 모여서 만든 흐름이며, 그 흐름을 직접 추려내는 것이 글쓰기에서 가장 어려운 부분이기 때문이다.

#### 수용 기준

**AC-2.1 — 분석 실행 조건**
- **Given** 활동 데이터가 1건 이상 수집된 상태일 때
- **When** 사용자가 "분석" 버튼을 클릭하면
- **Then** 분석이 시작되고 진행 상태(로딩)가 표시된다
- **And** 활동 데이터가 0건이면 "분석" 버튼은 클릭할 수 없다

**AC-2.2 — 분석 결과 구성 요소**
- **Given** 분석이 정상 완료되었을 때
- **When** 결과가 화면에 렌더링되면
- **Then** 아래 3개 구성 요소가 모두 표시된다
  - [ ] **기간 요약**: 해당 기간 활동 전반을 서술한 3~5문장의 문단
  - [ ] **주요 하이라이트**: 가장 의미 있는 작업 3~5개를 항목별 목록으로 제시
  - [ ] **인사이트**: 활동 패턴에서 도출된 관찰 2개 이상 (예: 집중 기술 영역, 작업 성격의 변화)

**AC-2.3 — 근거 추적성**
- **Given** 분석 결과의 "주요 하이라이트"가 표시되었을 때
- **When** 각 하이라이트 항목을 확인하면
- **Then** 해당 항목이 어떤 활동(저장소명 또는 PR/이슈 제목)에서 도출되었는지 근거가 함께 표시되어, 사용자가 사실 여부를 검증할 수 있다

**AC-2.4 — 한국어 출력**
- **Given** 분석이 완료되었을 때
- **When** 결과 텍스트를 확인하면
- **Then** 요약·하이라이트·인사이트가 모두 한국어로 작성되어 있다 (커밋 메시지·저장소명 등 고유명사는 원문 유지)

**AC-2.5 — 응답 시간 및 타임아웃**
- **Given** 사용자가 분석을 실행했을 때
- **When** 60초 이내에 응답이 도착하지 않으면
- **Then** 요청을 중단하고 "분석에 시간이 너무 오래 걸립니다. 기간을 줄이거나 다시 시도해 주세요."라는 메시지와 재시도 버튼을 표시한다

**AC-2.6 — API 오류 처리**
- **Given** Gemini API 호출이 실패했을 때(rate limit, 인증 오류, 서버 오류 등)
- **When** 오류가 발생하면
- **Then** "AI 분석에 실패했습니다."라는 메시지와 재시도 버튼이 표시되고, **F1에서 수집한 활동 데이터는 화면에서 사라지지 않고 유지된다**

**AC-2.7 — API 키 비노출**
- **Given** 애플리케이션이 브라우저에서 실행 중일 때
- **When** 브라우저 개발자 도구의 네트워크 탭과 클라이언트 번들 소스를 검사하면
- **Then** Gemini API 키가 어디에서도 노출되지 않는다 (Gemini 호출은 서버 측에서만 수행)

**AC-2.8 — 재분석**
- **Given** 이미 분석 결과가 표시된 상태일 때
- **When** 사용자가 기간을 변경하거나 "다시 분석"을 실행하면
- **Then** 새 분석 결과로 갱신되며, 이전 결과는 대체된다

### F3. 플랫폼별 콘텐츠 자동 생성

#### 개요

F2의 분석 결과를 바탕으로 LinkedIn / X / 블로그 각각의 길이와 톤에 맞는 콘텐츠 초안을 생성한다. 사용자는 화면에서 직접 수정하고 복사할 수 있다.

#### 사용자 스토리

> **개인 개발자로서**, 하나의 분석 결과로 LinkedIn·X·블로그 세 플랫폼의 초안을 한 번에 받고 싶다. **왜냐하면** 각 플랫폼은 요구하는 길이와 톤이 완전히 달라서, 같은 소재를 세 번 다시 쓰는 일이 실제 발행을 포기하게 만드는 가장 큰 이유이기 때문이다.

#### 수용 기준

**AC-3.1 — 생성 실행 조건**
- **Given** F2 분석 결과가 존재하는 상태일 때
- **When** 사용자가 "콘텐츠 생성"을 실행하면
- **Then** 3개 플랫폼용 초안 생성이 시작된다
- **And** 분석 결과가 없으면 "콘텐츠 생성" 버튼은 클릭할 수 없다

**AC-3.2 — 3개 플랫폼 동시 출력**
- **Given** 콘텐츠 생성이 완료되었을 때
- **When** 결과 화면을 확인하면
- **Then** LinkedIn / X / 블로그 3개 초안이 각각 구분된 영역(탭 또는 카드)에 모두 표시된다

**AC-3.3 — 플랫폼별 형식 요건**

| 플랫폼 | 분량 기준 | 톤·구조 요건 |
|---|---|---|
| **LinkedIn** | 600~1,300자 (한글 기준) | 전문적·1인칭 서술. 도입 훅 → 작업 내용 → 배운 점/성과 구조. 해시태그 3~5개 포함 |
| **X** | 280자 이내 (공백 포함) | 간결·후킹형. 핵심 성과 1개에 집중. 해시태그 1~2개 |
| **블로그** | 800자 이상 | 제목 + 소제목(H2 이상) 2개 이상을 포함한 마크다운 구조. 도입-본문-마무리 구성 |

- **Given** 콘텐츠 생성이 완료되었을 때
- **When** 각 플랫폼 초안의 분량과 구조를 확인하면
- **Then** 위 표의 기준을 각각 충족한다
- **And** X 초안이 280자를 초과하는 경우 화면에 글자 수 초과 경고가 표시된다

**AC-3.4 — 글자 수 표시**
- **Given** 초안이 표시된 상태일 때
- **When** 각 플랫폼 영역을 확인하면
- **Then** 현재 글자 수가 표시되며, 사용자가 텍스트를 수정하면 실시간으로 갱신된다

**AC-3.5 — 수정 가능**
- **Given** 생성된 초안이 표시된 상태일 때
- **When** 사용자가 초안 텍스트 영역을 클릭해 내용을 편집하면
- **Then** 편집한 내용이 그대로 반영되고, 편집 중 다른 플랫폼의 초안은 영향을 받지 않는다

**AC-3.6 — 복사**
- **Given** 초안(원본 또는 사용자가 수정한 버전)이 표시된 상태일 때
- **When** 사용자가 해당 플랫폼의 "복사" 버튼을 클릭하면
- **Then** 현재 화면에 표시된 내용이 클립보드에 복사되고, "복사되었습니다" 피드백이 표시된다

**AC-3.7 — 개별 재생성**
- **Given** 3개 초안이 생성된 상태일 때
- **When** 사용자가 특정 플랫폼의 "다시 생성"을 실행하면
- **Then** 해당 플랫폼 초안만 새로 생성되고, 나머지 두 플랫폼의 내용(사용자 수정분 포함)은 유지된다

**AC-3.8 — 사실 기반 생성**
- **Given** 콘텐츠가 생성되었을 때
- **When** 초안에 언급된 저장소명·PR 제목·기술 스택을 F1 활동 데이터와 대조하면
- **Then** 수집된 활동 데이터에 존재하지 않는 저장소명이나 수치가 포함되어 있지 않다
- **And** 화면에 "AI가 생성한 초안입니다. 게시 전 내용을 확인해 주세요."라는 안내 문구가 상시 표시된다

**AC-3.9 — 브라우저 로컬 임시 보존**
- **Given** 콘텐츠를 생성하고 일부를 수정한 상태일 때
- **When** 사용자가 페이지를 새로고침하면
- **Then** 직전에 생성·수정한 콘텐츠가 복원되어 표시된다 (브라우저 로컬 저장 기반)
- **And** 사용자가 로그아웃하거나 "초기화"를 실행하면 로컬에 보존된 내용이 삭제된다

**AC-3.10 — 생성 오류 처리**
- **Given** 콘텐츠 생성 중 일부 플랫폼에서 오류가 발생했을 때
- **When** 결과가 렌더링되면
- **Then** 성공한 플랫폼의 초안은 정상 표시되고, 실패한 플랫폼 영역에만 오류 메시지와 재시도 버튼이 표시된다

## 4. 성공 기준

### 4.1 제품 성공 지표 (Primary)

| # | 지표 | 목표값 | 측정 방법 |
|---|---|---|---|
| M1 | **End-to-End 완료 시간** — 로그인부터 3개 초안 확보까지 | **5분 이내** | 사용자가 직접 스톱워치로 3회 측정, 평균값 |
| M2 | **초안 채택률** — 생성된 초안 중 30% 미만 수정으로 실제 게시 가능한 비율 | **3개 중 2개 이상** | 사용자가 초안별로 "수정 없이 사용 가능 / 소폭 수정 / 전면 재작성" 3단계 평가 |
| M3 | **사실 정확도** — 생성 콘텐츠에 실제 활동에 없는 내용(환각)이 포함되지 않음 | **오류 0건 / 10회 생성** | 초안의 저장소명·수치를 F1 원시 데이터와 수동 대조 |
| M4 | **실제 발행 전환** — 도구를 사용해 실제로 플랫폼에 게시한 횟수 | **월 2회 이상** | 사용자 자가 기록 |

### 4.2 기술 품질 지표 (Secondary)

| # | 지표 | 목표값 | 측정 방법 |
|---|---|---|---|
| M5 | 활동 데이터 조회 완료 시간 (최근 30일 기준) | 10초 이내 | 브라우저 네트워크 탭 측정 |
| M6 | AI 분석(F2) 응답 시간 | 30초 이내 (타임아웃 60초) | 요청~응답 시간 측정 |
| M7 | 콘텐츠 생성(F3) 응답 시간 | 45초 이내 | 요청~응답 시간 측정 |
| M8 | 처리되지 않은 오류로 인한 화면 중단(흰 화면) | 0건 | 정상 흐름 + 오류 시나리오 각 5회 수동 테스트 |
| M9 | 클라이언트 측 API 키 노출 | 0건 | 브라우저 번들 및 네트워크 요청 검사 |

### 4.3 MVP 완료 판정 기준 (Definition of Done)

MVP는 아래를 **모두** 충족할 때 완료로 판정한다.

- [ ] F1 / F2 / F3의 모든 수용 기준(AC-1.x, AC-2.x, AC-3.x)이 통과함
- [ ] 로그인 → 수집 → 분석 → 생성 → 복사 전체 흐름이 중단 없이 1회 완주됨
- [ ] M1(5분 이내), M3(환각 0건), M8(중단 0건), M9(키 노출 0건) 충족
- [ ] 주요 실패 시나리오(OAuth 거부, rate limit, AI API 오류, 활동 0건)가 각각 사용자에게 이해 가능한 메시지로 처리됨

## 5. Out of Scope (명시적 제외)

아래 항목은 **MVP에서 의도적으로 제외**한다. "나중에 할 것"이 아니라 "MVP 판정에 포함하지 않을 것"이라는 뜻이며, 이 목록에 있는 기능을 구현했다는 이유로 MVP 완료가 지연되어서는 안 된다.

### 5.1 데이터 저장 관련

| 제외 항목 | 사유 |
|---|---|
| **데이터베이스 도입** | 1인 사용자, 매번 GitHub에서 최신 데이터 조회로 충분. DB는 운영 부담만 추가 |
| **생성 콘텐츠 영구 히스토리 관리** | 과거 생성물 목록·검색·비교 기능 없음. 브라우저 로컬 임시 보존(AC-3.9)이 전부이며, 브라우저 데이터 삭제 시 함께 사라짐 |
| **활동 데이터 캐싱 레이어** | 중복 조회 최적화는 성능 문제가 실제로 관측된 후 판단 |
| **버전 관리 / 초안 비교** | 이전 버전 복원, diff 보기 등 미지원 |

### 5.2 사용자 / 권한 관련

| 제외 항목 | 사유 |
|---|---|
| **팀 / 조직 계정 지원** | 대상 사용자 1명. 다중 사용자 데이터 격리 설계 불필요 |
| **역할 기반 권한(RBAC)** | 역할 개념 자체가 없음 |
| **GitHub 외 로그인 수단** | 이메일/구글/자체 회원가입 미지원 |
| **다중 GitHub 계정 연결** | 로그인한 계정 1개만 대상 |

### 5.3 콘텐츠 / 발행 관련

| 제외 항목 | 사유 |
|---|---|
| **실제 SNS 자동 게시** | LinkedIn/X API 연동, OAuth 추가 승인, 플랫폼 심사 절차가 필요. MVP는 **복사·붙여넣기**까지만 |
| **예약 발행 / 스케줄링** | 자동 게시가 없으므로 성립하지 않음 |
| **발행 후 성과 분석** | 조회수·좋아요·팔로워 증감 추적 미지원 |
| **이미지 / 썸네일 자동 생성** | 텍스트 초안만 생성 |
| **다국어 콘텐츠 생성** | 한국어만. 영어 초안 생성 미지원 |
| **커스텀 톤·페르소나 설정 UI** | 플랫폼별 톤은 시스템이 고정. 사용자 조정 불가 |

### 5.4 데이터 범위 관련

| 제외 항목 | 사유 |
|---|---|
| **비공개(private) 저장소 활동 분석** | 기본 조회 범위는 공개 저장소 활동. 비공개 저장소 접근은 OAuth 스코프 확대와 정보 노출 검토가 필요하므로 MVP 제외 (→ 8장 미해결 질문 Q1) |
| **코드 내용(diff) 자체의 분석** | 커밋 메시지·PR/이슈 제목·메타데이터만 사용. 실제 코드 변경 내용은 분석하지 않음 |
| **GitHub 외 데이터 소스** | GitLab, Bitbucket, Jira 등 미연동 |
| **기여 그래프 시각화** | 차트·그래프 등 데이터 시각화 미포함. 건수와 목록 표시로 충분 |

### 5.5 운영 관련

| 제외 항목 | 사유 |
|---|---|
| **다국어 UI (i18n)** | 한국어 UI만 |
| **모바일 전용 최적화** | 데스크톱 브라우저 우선. 모바일은 동작하면 좋으나 검증 대상 아님 |
| **사용량/비용 대시보드** | API 호출량·비용 추적 UI 미포함 |
| **알림 / 리마인더** | "이번 주 콘텐츠 만들 시간입니다" 같은 푸시·이메일 알림 없음 |

## 6. 가정 및 제약

### 6.1 GitHub API 관련

| # | 항목 | 내용 | 대응 |
|---|---|---|---|
| C1 | **Rate Limit** | 인증된 사용자 기준 시간당 5,000 요청. 개인 사용(주 1~2회)에서는 여유가 크나, 저장소가 많거나 기간이 길면 다수 요청이 발생할 수 있음 | 기간 옵션을 7/30/90일로 제한. rate limit 초과 시 명시적 오류 메시지(AC-1.8) |
| C2 | **활동 이벤트 조회 범위 제한** | GitHub Events API는 최근 약 90일 / 최대 300건까지만 반환. 그 이전 활동은 조회 불가 | 기간 선택 최댓값을 90일로 설정. 이 범위를 넘는 요구는 MVP 대상 아님 |
| C3 | **공개 저장소 범위** | 기본 OAuth 스코프에서는 공개 저장소 활동만 안정적으로 조회 가능 | 비공개 저장소는 Out of Scope(5.4). 화면에 "공개 저장소 활동 기준"임을 명시 |
| C4 | **데이터 반영 지연** | GitHub API의 활동 데이터는 실시간이 아니며 수 분의 지연이 있을 수 있음 | 방금 만든 커밋이 즉시 반영되지 않을 수 있음을 감안. 별도 대응 없음 |
| C5 | **커밋 메시지 품질 의존** | 커밋 메시지가 부실하면(`fix`, `wip` 등) AI 분석 품질이 직접적으로 저하됨 | 제품이 통제할 수 없는 입력 품질 문제. PR/이슈 제목을 보조 소재로 함께 활용 |

### 6.2 Gemini API 관련

| # | 항목 | 내용 | 대응 |
|---|---|---|---|
| C6 | **비용 발생** | 분석(F2) 1회 + 콘텐츠 생성(F3) 3개 = 세션당 최소 2회 이상의 API 호출. 재생성 시 추가 발생 | 개인 사용 빈도(월 2~8세션)에서는 비용이 미미하다고 가정. 비용 추적 UI는 Out of Scope |
| C7 | **응답 지연** | LLM 응답은 수 초~수십 초 소요. 사용자가 즉시 결과를 볼 수 없음 | 로딩 상태 필수 표시(AC-1.6, AC-2.1). 타임아웃 60초(AC-2.5) |
| C8 | **출력 비결정성** | 같은 입력에도 매번 다른 결과가 생성됨 | 사양이 아닌 특성으로 수용. 재생성 기능(AC-3.7)으로 사용자가 대안을 얻도록 지원 |
| C9 | **환각(Hallucination) 위험** | 활동 데이터에 없는 기술명·수치·성과를 생성할 가능성 | 근거 추적성(AC-2.3), 사실 기반 검증(AC-3.8), 상시 안내 문구로 대응. **완전 방지는 불가능하며 최종 검증 책임은 사용자에게 있음** |
| C10 | **API 키 보안** | Gemini API 키가 클라이언트에 노출되면 무단 사용 가능 | 서버 측에서만 호출(AC-2.7). 환경 변수로 관리하며 저장소에 커밋 금지 |
| C11 | **입력 토큰 한도** | 활동 데이터가 많으면 프롬프트 길이가 한도를 초과할 수 있음 | 기간 90일 상한 및 항목 수 제한으로 완화. 초과 시 상위 N건만 사용하는 방식은 TECH_SPEC에서 결정 |

### 6.3 제품 / 운영 가정

| # | 가정 | 근거 및 영향 |
|---|---|---|
| A1 | 사용자는 **1명**이며 동시 접속·부하를 고려할 필요가 없다 | 인증·권한·확장성 설계를 단순화하는 핵심 근거 |
| A2 | 사용자는 **데스크톱 브라우저**에서 사용한다 | 모바일 최적화 미검증(5.5) |
| A3 | 사용자는 **GitHub 계정을 보유**하고 있으며 OAuth 개념에 익숙하다 | 온보딩·튜토리얼 화면 불필요 |
| A4 | 생성 결과가 **세션 종료 시 사라져도 무방**하다 | 사용자가 필요한 내용은 즉시 복사해 각 플랫폼에 붙여넣기 때문. DB 미도입의 근거 |
| A5 | 생성물은 **초안**이며 그대로 발행하지 않고 사용자가 검토·수정한다 | 환각 위험(C9)의 잔여 리스크를 사용자 검토로 흡수 |
| A6 | 로컬 개발 환경 또는 개인용 배포 환경에서 실행되며 **공개 서비스로 운영되지 않는다** | 인증 강화, 남용 방지, 요금 한도 관리 등의 요구가 발생하지 않음 |

### 6.4 기술 방향 (상세 설계는 TECH_SPEC에 위임)

> 아래는 제품 요구사항에서 파생되는 **제약 조건**만 명시한다. 아키텍처·데이터 흐름·모듈 구조·API 설계 등 구현 상세는 **TECH_SPEC(`/sdd-design`)** 에서 결정한다.

- **프레임워크**: Next.js 풀스택 (App Router + Route Handlers). 별도 백엔드 서버를 두지 않는다.
- **AI 호출 위치**: Gemini API 호출은 **반드시 서버 측**에서만 수행한다 (AC-2.7, C10).
- **저장소**: 데이터베이스를 사용하지 않는다. 상태는 세션 및 브라우저 로컬 저장에 한정한다.
- **UI 언어**: 한국어.

## 7. 사용자 흐름 요약

```
1. 접속           → 로그인 전 화면 ("GitHub으로 로그인")
2. OAuth 인증     → GitHub 동의 → 대시보드 진입 (아바타·ID 표시)
3. 기간 선택      → 최근 7일(기본) / 30일 / 90일
4. 활동 수집      → 커밋·PR·이슈·스타 건수 + 저장소 목록 표시       [F1]
5. 분석 실행      → 기간 요약 · 하이라이트 · 인사이트 생성            [F2]
6. 콘텐츠 생성    → LinkedIn / X / 블로그 3개 초안 동시 출력          [F3]
7. 수정           → 화면에서 직접 편집 (글자 수 실시간 표시)
8. 복사           → 플랫폼별 복사 → 사용자가 실제 SNS에 붙여넣기
```

**중단 지점 처리**: 4~6단계 중 어느 곳에서 오류가 발생해도 이전 단계의 결과는 화면에 유지되며(AC-2.6, AC-3.10), 사용자는 실패한 단계만 재시도할 수 있다.

## 8. 미해결 질문

MVP 개발을 시작하기 전 또는 진행 중에 결정이 필요한 항목. **각 항목에는 결정이 지연될 경우의 기본값(fallback)을 함께 명시**하여, 답이 나오지 않아도 개발이 멈추지 않도록 한다.

| # | 질문 | 영향 범위 | 결정 시점 | 미결 시 기본값 |
|---|---|---|---|---|
| Q1 | 비공개 저장소 활동을 포함할 것인가? 포함한다면 OAuth 스코프를 `repo`까지 확대하고, 저장소명 노출 여부를 사용자가 제어해야 하는가? | F1 (OAuth 스코프), 5.4 | MVP 이후 | **공개 저장소만 조회.** 화면에 범위 명시 |
| Q2 | 활동 데이터 중 AI 분석에 실제로 투입할 항목과 상한선은? (예: 커밋 최대 100건, PR 전체 등) | F2 프롬프트 설계, C11 | TECH_SPEC 단계 | 커밋은 최근 100건, PR·이슈는 전체, 스타는 저장소명만 |
| Q3 | 분석(F2)과 콘텐츠 생성(F3)을 별도 액션으로 둘 것인가, "한 번에 생성"으로 통합할 것인가? | UX 흐름, M1(5분 목표) | MVP 구현 중 | **별도 2단계 유지.** 분석 결과를 확인한 뒤 생성 여부를 판단할 수 있어 환각 검증에 유리 |
| Q4 | 블로그 초안의 상세도 수준 — 전체 글인가, 개요(outline) 수준인가? | AC-3.3 | MVP 구현 중 | **800자 이상의 초안 형태.** 개요만으로는 초안 채택률(M2) 달성이 어려움 |
| Q5 | 브라우저 로컬 저장(AC-3.9)의 보존 기간과 용량 상한은? | F3 | TECH_SPEC 단계 | 최근 1세션 분량만 보존. 새 생성 시 덮어쓰기 |
| Q6 | 활동이 극히 적은 기간(예: 커밋 2건)에도 콘텐츠를 생성할 것인가? | F2, F3 | MVP 구현 중 | 생성하되, "활동량이 적어 초안 품질이 낮을 수 있습니다" 안내 표시 |
| Q7 | 배포 환경 — 로컬 실행만인가, Vercel 등에 개인 배포하는가? 배포 시 접근 제한(본인만 로그인 가능)을 어떻게 강제하는가? | 인증, A6 | TECH_SPEC 단계 | 로컬 실행 기준으로 개발. 배포 시 GitHub 로그인 ID 화이트리스트로 제한 |
